企业做 AI，预算争议经常不是出在“要不要做”，而是出在“按什么方式做”。同一句话——“帮我们把智能体落地”——用项目制报价和用 FDE 报价，范围与风险完全不同。

**先给结论：范围清晰、接口清楚，用项目制；现场复杂、需求会变、要持续推进生产指标，用 FDE。** 两者之间，可以先小项目制尖刀，再 FDE 扩面。

## 一眼对比（决策者版）

| 你在意的事 | 选项目制，如果… | 选 FDE，如果… |
| --- | --- | --- |
| 范围 | 能写成功能清单并锁住 | 目标明确，路径要边做边收敛 |
| 现场 | 远程为主、节点到场就够 | 需要常驻或高密度驻场 |
| 规则变了怎么办 | 走变更单，可接受等待 | 现场优先排序，快速验证 |
| 什么叫成功 | 验收用例过了 | 业务指标改善 + 系统真在用 |
| 内部能不能接手 | 文档 + 培训即可 | 需要边做边带教 |
| 钱怎么付 | 按项目（如 Agent 标准版 ¥50,000 起） | 按月（¥50,000/月起） |
| 典型节奏 | 4–12 周一次性冲刺 | 按月续作，持续迭代 |

## 选错模式，具体会贵在哪

**该项目制却上了 FDE：**  
某公司制度问答范围已经锁死——200 份文档、一个内网入口、接口可导出。却按月驻场三个月。人在现场，第二周活就定死了，后半段变成“有人坐着等零星改动”。浪费的不是工程师能力，而是用高密度推进力去干本可一次验收的活。三个月月费买到的，其实是一个本该用项目制锁总价就能结清的知识库问答。

**该 FDE 却死守项目制：**  
某工厂 PoC 过了“质检助手”，生产对接却要同时协调质量、车间、IT 三个系统，规则写在班组长脑子里。合同按固定范围远程交付，每改一次流程就开变更单。两个月后，变更预算吃掉原合同相当一部分，系统仍进不了日常班次——错过的是一个生产旺季窗口，而不只是多付一个月费用。

还有第三种浪费：**名义上 FDE，实际上当驻场客服。** 工程师每天在修打印驱动、改报表格式，主目标（例如“质检记录问答进班组”）却从未进周会。模式名字对了，目标管理错了，一样烧钱。

选错模式的代价，通常不是“多付一点钱”，而是**错过一个业务季**，或把团队耗在变更战争里。

## 用不确定性定价，别用日历硬比

把 FDE 月费乘三个月，再和项目制总价比，是常见但粗糙的算法。更合理的算法是：

- **项目制：** 范围锁定后的交付成本 + 变更成本的期望值；
- **FDE：** 达到同一业务指标所需的月份 × 月费 + 客户侧配合成本。

变更期望很高时，项目制“看起来便宜”会被变更单吃掉；范围极清晰时，FDE 可能买过了。

可操作的粗算法：先估计“未来三个月规则 / 接口大改的次数”。若你心里觉得会频繁改，优先按 FDE 或“小项目制 + 预留变更缓冲”算；若你确信三个月内输入输出几乎不动，优先项目制锁总价。

参考公开标价带（细节以 [服务价格](/pricing) 为准）：

- 项目制尖刀：Agent 标准版 ¥50,000 起、RAG ¥20,000 起、企业版 ¥120,000 起；
- FDE：¥50,000/月起。

数字只是尺子，不是答案——同一把尺子，量不同不确定性，结论会反过来。

## 合同怎么钉，才不容易模式漂移

无论选哪种，建议书面钉住：

- 本阶段主目标（一句话）；
- 不在范围内的事（同样重要）；
- 客户侧配合清单；
- 周 / 月沟通机制；
- 变更如何计费，或如何重排优先级；
- 知识归属与交接物。

项目制怕的是范围蔓延；FDE 怕的是目标发散。文字把边界钉住，现场才能跑得快。沟通早期我们也会明确建议一种主模式，并写清为什么不选另一种、月度或项目如何验收、客户侧必须提供的配合、退出与续约机制——把模式选对，往往比把日费率砍低更省钱。

## 决策会上只留五句话

1. 下周业务规则变了，我们能否承受走变更流程的速度？
2. 现场有没有能拍板的业务 owner？
3. 最大风险是编码量，还是组织与系统未知？
4. 成功是“上线功能”，还是“某个业务数字改善”？
5. 内部团队是否需要被带教到能接手？

若 3、4、5 偏向复杂与长期，FDE 优先。CTO 只给你三十秒时，把开头那句结论写进纪要即可：范围清、接口清、要可控总价 → 项目制；现场乱、规则变、要推进生产指标 → FDE；两者之间 → 先小项目制尖刀，再 FDE 扩面。
